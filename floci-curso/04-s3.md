# Módulo 04 — S3 (Simple Storage Service)

> **Objetivo**: entender cómo funciona el almacenamiento de objetos en AWS y practicarlo en Floci. S3 es uno de los servicios más usados de AWS y aparece en muchísimas preguntas del examen.

Tiempo estimado: 1.5 a 2 horas.

---

## 1. ¿Qué es S3?

**Amazon S3** (Simple Storage Service) es un servicio de **almacenamiento de objetos**. Pensalo como un disco rígido infinito en la nube, al que accedés por HTTP en lugar de por un sistema de archivos.

Algunos casos de uso típicos:

- Hosting de sitios web estáticos (HTML, CSS, JS).
- Imágenes, videos, PDFs subidos por usuarios de tu app.
- Backups de bases de datos.
- Logs de aplicaciones.
- Almacenamiento intermedio para pipelines de datos.
- Data lakes (junto con servicios analíticos).

### ¿Qué significa "almacenamiento de objetos"?

Hay tres maneras principales de almacenar datos:

| Tipo                    | Cómo accedés                              | Ejemplos                  |
|-------------------------|-------------------------------------------|---------------------------|
| **Archivo (file)**      | Por path en un filesystem                 | NTFS, NFS, AWS EFS        |
| **Bloque (block)**      | Como un disco rígido, en bloques crudos   | AWS EBS, iSCSI            |
| **Objeto (object)**     | Por una key (clave) vía API HTTP          | **AWS S3**, Google Cloud Storage |

En S3, **cada archivo es un "objeto"** y se identifica por:

- Un **bucket** (espacio de nombres global, único en todo AWS).
- Una **key** (parecido a un path: `usuarios/123/foto.jpg`).

Aunque la key tenga `/`, **S3 no tiene carpetas reales**. Es solo una key plana con barras dentro. La consola web te lo muestra como carpetas para que sea cómodo, pero internamente es plano.

## 2. Conceptos clave

### 2.1 — Buckets

Un **bucket** es el contenedor de tus objetos. Características:

- **Nombre globalmente único** (en AWS real, no podés crear un bucket con un nombre que ya exista en otra cuenta). En Floci es local a tu instancia.
- **Pertenece a una región** (excepto en Floci, donde la región es nominal).
- Reglas de naming: 3 a 63 caracteres, minúsculas, números, guiones. Sin puntos al inicio/fin.

### 2.2 — Objetos

Cada objeto tiene:

- **Key**: la "ruta" dentro del bucket (`fotos/2024/perro.jpg`).
- **Value**: el contenido binario (hasta 5 TB por objeto).
- **Version ID** (si tenés versioning activo).
- **Metadata**: HTTP headers + custom metadata.
- **Storage class**: el tier de costos/performance.

### 2.3 — Storage classes (entra en el examen)

S3 tiene varias clases de almacenamiento con distintos costos y latencias:

| Storage class           | Para qué                                  | Latencia    | Costo  |
|-------------------------|-------------------------------------------|-------------|--------|
| `STANDARD`              | Acceso frecuente, defaultedo              | Milisegundos| $$$    |
| `STANDARD_IA`           | Acceso poco frecuente (Infrequent Access) | Milisegundos| $$     |
| `ONEZONE_IA`            | IA en una sola AZ (más barato, menos durable) | Milisegundos | $$    |
| `INTELLIGENT_TIERING`   | S3 elige por vos según patrón de acceso   | Milisegundos| $$$    |
| `GLACIER_INSTANT`       | Archivos con acceso ocasional             | Milisegundos| $      |
| `GLACIER_FLEXIBLE`      | Backups, recuperación en minutos a horas  | Minutos-horas | $    |
| `GLACIER_DEEP_ARCHIVE`  | Archivos legales, 7+ años                 | 12 horas    | $      |

Floci acepta el atributo `StorageClass` en las requests pero todo se guarda igual (no hay "tiering" real). Para el examen igual tenés que conocerlos.

### 2.4 — Versioning

Si activás **versioning** en un bucket, cada vez que sobrescribís un objeto, S3 guarda la versión anterior en lugar de borrarla. Te permite:

- Recuperar archivos sobrescritos por error.
- Mantener un histórico.
- "Borrar" objetos sin perderlos realmente (genera un "delete marker").

**No se puede desactivar** una vez activado, solo se puede **suspender** (lo cual deja de generar versiones nuevas pero no borra las viejas).

### 2.5 — Pre-signed URLs

Una URL firmada con tus credenciales que **permite a alguien sin permisos** acceder a un objeto durante un tiempo limitado.

Caso típico: tu app web necesita que un usuario suba una foto. En lugar de que la foto pase por tu backend (consumiendo ancho de banda y memoria), tu backend genera un pre-signed URL de tipo `PUT`, se lo manda al frontend, y el frontend sube directo a S3.

### 2.6 — Object Lock

Permite "congelar" un objeto para que **nadie pueda borrarlo ni modificarlo** durante un período. Útil para compliance (banca, salud, etc.). Tiene dos modos:

- **GOVERNANCE**: usuarios con permisos especiales pueden eliminar el lock.
- **COMPLIANCE**: nadie puede eliminar el lock, ni siquiera la root account.

### 2.7 — Bucket policies vs ACLs

Dos formas de controlar acceso a buckets/objetos:

- **Bucket policies**: documentos JSON tipo IAM, atachados al bucket. La forma moderna y recomendada.
- **ACLs (Access Control Lists)**: legacy, en deshuso. Casi no se usan.

### 2.8 — Encriptación

S3 puede encriptar los datos en reposo. Opciones:

- **SSE-S3**: AWS administra las claves automáticamente.
- **SSE-KMS**: usás KMS para administrar las claves (más control, auditable).
- **SSE-C**: vos pasás la clave en cada request.
- **Client-side**: encriptás antes de subir.

Desde 2023, S3 encripta **por defecto** todos los objetos nuevos con SSE-S3 sin que hagas nada.

### 2.9 — Event notifications

Podés configurar el bucket para que cuando pase algo (subida de objeto, borrado, etc.), mande un evento a:

- Una cola SQS.
- Un topic SNS.
- Una función Lambda.

Caso típico: cuando se sube una imagen al bucket, una Lambda la procesa (resize, thumbnail, OCR, etc.).

## 3. Cómo lo emula Floci

Floci implementa **30 operaciones de S3** y cubre:

- ✅ CRUD básico de buckets y objetos.
- ✅ Multipart upload (para objetos grandes).
- ✅ Versioning completo.
- ✅ Pre-signed URLs.
- ✅ Object Lock (GOVERNANCE y COMPLIANCE).
- ✅ Event notifications (a SQS, SNS, Lambda).
- ✅ Bucket policies.

Diferencias con AWS real:

- **No hay storage classes reales**: aceptás el campo pero todo se guarda igual.
- **No hay replicación cross-region**.
- **No hay analytics/inventory** (S3 Storage Lens, etc.).
- **No hay Transfer Acceleration**.

### Configuración importante: `forcePathStyle`

S3 tiene dos formas de armar las URLs:

- **Virtual-hosted style** (default en AWS real): `https://mi-bucket.s3.amazonaws.com/foto.jpg`
- **Path style** (legacy pero el que usa Floci): `http://localhost:4566/mi-bucket/foto.jpg`

Esto importa cuando usás el SDK: tenés que pasar `forcePathStyle: true`. En el CLI no hace falta, lo maneja solo.

## 4. Laboratorio práctico

### Lab 1 — Crear y listar buckets

```bash
# Crear un bucket
aws s3 mb s3://mi-curso

# Listarlos
aws s3 ls

# Verificarlo con la API de bajo nivel
aws s3api list-buckets
```

> 💡 `aws s3` es el "comando de alto nivel" (más fácil). `aws s3api` es la API completa (más opciones). Para cosas avanzadas vas a usar `s3api`.

### Lab 2 — Subir, descargar y listar objetos

```bash
# Crear un archivo de prueba
echo "Hola Floci" > saludo.txt

# Subir
aws s3 cp saludo.txt s3://mi-curso/saludo.txt

# Listar el contenido del bucket
aws s3 ls s3://mi-curso/

# Descargar (a otro nombre)
aws s3 cp s3://mi-curso/saludo.txt saludo-bajado.txt
cat saludo-bajado.txt
```

### Lab 3 — Subir una "carpeta" entera

```bash
mkdir -p sitio/css sitio/img
echo "<h1>Hola</h1>" > sitio/index.html
echo "body { color: red; }" > sitio/css/style.css

# Sync sube todo de manera recursiva
aws s3 sync ./sitio s3://mi-curso/sitio/

# Listar recursivo
aws s3 ls s3://mi-curso/sitio/ --recursive
```

Vas a ver que las "carpetas" `css/` e `img/` no existen como tales — solo hay objetos con `/` en la key.

### Lab 4 — Versioning

Activar versioning en el bucket:

```bash
aws s3api put-bucket-versioning \
  --bucket mi-curso \
  --versioning-configuration Status=Enabled
```

Subir el mismo archivo varias veces con contenido distinto:

```bash
echo "Versión 1" > archivo.txt
aws s3 cp archivo.txt s3://mi-curso/archivo.txt

echo "Versión 2" > archivo.txt
aws s3 cp archivo.txt s3://mi-curso/archivo.txt

echo "Versión 3" > archivo.txt
aws s3 cp archivo.txt s3://mi-curso/archivo.txt
```

Listar todas las versiones:

```bash
aws s3api list-object-versions --bucket mi-curso --prefix archivo.txt
```

Descargar una versión específica (necesitás el VersionId de la salida anterior):

```bash
aws s3api get-object \
  --bucket mi-curso \
  --key archivo.txt \
  --version-id <VERSION-ID> \
  archivo-vieja.txt

cat archivo-vieja.txt
```

### Lab 5 — Pre-signed URLs

Generar un URL de descarga válido por 1 hora:

```bash
aws s3 presign s3://mi-curso/saludo.txt --expires-in 3600
```

Output:

```
http://localhost:4566/mi-curso/saludo.txt?AWSAccessKeyId=...&Signature=...&Expires=...
```

Probalo con `curl`:

```bash
curl "<el URL de arriba>"
```

Te tiene que devolver "Hola Floci".

### Lab 6 — Bucket policy

Vamos a hacer el bucket "público para lectura" (escenario típico de hosting de sitio web estático).

`bucket-policy.json`:

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "PublicReadGetObject",
      "Effect": "Allow",
      "Principal": "*",
      "Action": "s3:GetObject",
      "Resource": "arn:aws:s3:::mi-curso/*"
    }
  ]
}
```

Aplicarla:

```bash
aws s3api put-bucket-policy \
  --bucket mi-curso \
  --policy file://bucket-policy.json
```

Leerla:

```bash
aws s3api get-bucket-policy --bucket mi-curso
```

> ⚠️ En AWS real esto haría tu bucket accesible al mundo. **Cuidado** con bucket policies como esta en producción — son la fuente más común de leaks de S3. En Floci no tiene riesgo, es solo tu máquina.

### Lab 7 — Object Lock

Crear un bucket con Object Lock (solo se puede activar al crear el bucket):

```bash
aws s3api create-bucket \
  --bucket bucket-bloqueado \
  --object-lock-enabled-for-bucket
```

Subir un objeto y bloquearlo en modo GOVERNANCE por 1 minuto:

```bash
echo "no me borres" > inmutable.txt

# Subir el objeto
aws s3 cp inmutable.txt s3://bucket-bloqueado/inmutable.txt

# Bloquearlo (necesitás el VersionId del objeto recién subido)
VERSION_ID=$(aws s3api list-object-versions --bucket bucket-bloqueado --prefix inmutable.txt --query 'Versions[0].VersionId' --output text)

aws s3api put-object-retention \
  --bucket bucket-bloqueado \
  --key inmutable.txt \
  --version-id "$VERSION_ID" \
  --retention "Mode=GOVERNANCE,RetainUntilDate=2026-12-31T00:00:00Z"
```

Intentar borrarlo (debería fallar):

```bash
aws s3api delete-object \
  --bucket bucket-bloqueado \
  --key inmutable.txt \
  --version-id "$VERSION_ID"
```

### Lab 8 — Limpiar

```bash
# Borrar TODOS los objetos de un bucket (incluidos versionados)
aws s3 rm s3://mi-curso --recursive

# Para buckets con versioning, hay que borrar también las versiones:
aws s3api delete-objects --bucket mi-curso \
  --delete "$(aws s3api list-object-versions --bucket mi-curso \
  --query='{Objects: Versions[].{Key:Key,VersionId:VersionId}}')"

# Y los delete markers:
aws s3api delete-objects --bucket mi-curso \
  --delete "$(aws s3api list-object-versions --bucket mi-curso \
  --query='{Objects: DeleteMarkers[].{Key:Key,VersionId:VersionId}}')"

# Finalmente, borrar el bucket
aws s3 rb s3://mi-curso
```

Para el de Object Lock vas a tener que esperar a que expire la retención o (si fuera GOVERNANCE en AWS real) usar el flag `--bypass-governance-retention` con permisos especiales.

## 5. Bonus Node.js — App completa con S3

`s3-app.js`:

```js
import {
  S3Client,
  CreateBucketCommand,
  PutObjectCommand,
  GetObjectCommand,
  ListObjectsV2Command,
  DeleteObjectCommand,
} from "@aws-sdk/client-s3";
import { getSignedUrl } from "@aws-sdk/s3-request-presigner";
import { readFileSync } from "node:fs";

const s3 = new S3Client({
  endpoint: "http://localhost:4566",
  region: "us-east-1",
  credentials: { accessKeyId: "test", secretAccessKey: "test" },
  forcePathStyle: true,
});

const BUCKET = "node-bucket-demo";

// 1. Crear bucket (ignorar si ya existe)
try {
  await s3.send(new CreateBucketCommand({ Bucket: BUCKET }));
  console.log("Bucket creado");
} catch (err) {
  if (err.name !== "BucketAlreadyOwnedByYou") throw err;
  console.log("Bucket ya existía");
}

// 2. Subir un objeto
await s3.send(
  new PutObjectCommand({
    Bucket: BUCKET,
    Key: "hello.txt",
    Body: "Hola desde Node",
    ContentType: "text/plain",
  })
);
console.log("Objeto subido");

// 3. Listar objetos
const list = await s3.send(new ListObjectsV2Command({ Bucket: BUCKET }));
console.log(
  "Objetos en el bucket:",
  list.Contents?.map((o) => o.Key) ?? []
);

// 4. Generar pre-signed URL de descarga
const url = await getSignedUrl(
  s3,
  new GetObjectCommand({ Bucket: BUCKET, Key: "hello.txt" }),
  { expiresIn: 60 }
);
console.log("Pre-signed URL:", url);

// 5. Descargar y leer
const response = await s3.send(
  new GetObjectCommand({ Bucket: BUCKET, Key: "hello.txt" })
);
const body = await response.Body.transformToString();
console.log("Contenido descargado:", body);

// 6. Borrar
await s3.send(
  new DeleteObjectCommand({ Bucket: BUCKET, Key: "hello.txt" })
);
console.log("Objeto borrado");
```

```bash
npm install @aws-sdk/client-s3 @aws-sdk/s3-request-presigner
node s3-app.js
```

## 6. Patrones de uso reales

### Hosting de sitio web estático

1. Bucket con bucket policy de lectura pública.
2. Habilitar "static website hosting" en el bucket.
3. Subir `index.html`, CSS, JS.
4. (En AWS real) ponés CloudFront delante para HTTPS y caching.

### Upload de archivos de usuario

1. Frontend pide al backend "necesito subir una foto".
2. Backend genera pre-signed URL de tipo PUT, expira en 5 minutos.
3. Frontend sube directo a S3 con ese URL.
4. Backend recibe un event notification (vía Lambda) cuando se completó.
5. Lambda procesa la imagen (resize, mover a otro bucket, etcétera).

### Data lake

1. Buckets organizados por etapa: `raw/`, `cleaned/`, `enriched/`.
2. Pipelines (con Lambda, Glue, etc.) procesan datos de un bucket al siguiente.
3. Queries con Athena o Redshift Spectrum.

## 7. Diferencias clave con AWS real

| Aspecto                  | AWS real                                    | Floci                              |
|--------------------------|---------------------------------------------|------------------------------------|
| Nombre global de bucket  | Único en todo el planeta                    | Local a tu instancia               |
| Storage classes          | Costos y latencias reales                   | Solo aceptados nominalmente        |
| Transfer Acceleration    | Disponible                                  | No                                 |
| Replicación cross-region | Disponible                                  | No                                 |
| Encriptación             | SSE-S3, SSE-KMS, SSE-C reales               | Aceptados, no se encripta real     |
| Lifecycle policies       | Funcionan (mueven a Glacier, etc.)          | Aceptadas, no se ejecutan          |
| Tiempo a Glacier         | Minutos a 12 horas                          | Inmediato (no aplica)              |

## Quiz del módulo 04

**1.** ¿S3 tiene carpetas reales?

a) Sí, son obligatorias.
b) Sí, pero opcionales.
c) No, las "carpetas" son solo prefijos en las keys.
d) Sí, pero solo en algunas regiones.

**2.** ¿Cuál es el tamaño máximo de un objeto en S3?

a) 5 MB
b) 5 GB
c) 5 TB
d) No tiene límite

**3.** Si activás versioning en un bucket, ¿qué pasa cuando "borrás" un objeto?

a) Se borra para siempre.
b) Se crea un "delete marker" y la versión anterior queda recuperable.
c) Se mueve a otra región automáticamente.
d) S3 te pide confirmación antes de borrar.

**4.** ¿Para qué sirve un pre-signed URL?

a) Para acelerar las descargas.
b) Para encriptar el contenido.
c) Para permitirle a alguien sin credenciales acceder a un objeto durante un tiempo limitado.
d) Para hacer backups.

**5.** ¿Cuál es la storage class más barata para datos que casi nunca vas a leer?

a) S3 Standard
b) S3 Standard-IA
c) S3 Glacier Deep Archive
d) S3 Intelligent-Tiering

**6.** ¿Cuál de estos NO es un caso de uso típico de S3?

a) Hosting de sitio estático.
b) Backups.
c) Bases de datos relacionales.
d) Almacenamiento de imágenes subidas por usuarios.

**7.** En el SDK de Node.js para Floci, ¿qué opción tenés que pasarle al `S3Client`?

a) `useFloci: true`
b) `forcePathStyle: true`
c) `localMode: true`
d) Ninguna, funciona igual que con AWS.

---

### Respuestas

1. **c**. S3 es plano. Las "carpetas" son solo cómo la consola y los clientes representan keys con `/` adentro.
2. **c**. 5 TB por objeto. Más grande que eso necesitás dividir o usar multi-part upload con varios objetos.
3. **b**. Con versioning, "borrar" no borra: agrega un delete marker que oculta el objeto, pero las versiones anteriores siguen ahí.
4. **c**. Pre-signed URL = URL firmada con tus credenciales que le da acceso temporal a alguien que no tiene credenciales propias.
5. **c**. Glacier Deep Archive — la más barata, pero tarda hasta 12 horas en recuperar.
6. **c**. Para bases relacionales usás RDS, no S3. S3 es para objetos, no para SQL.
7. **b**. `forcePathStyle: true`. Floci no soporta el virtual-hosted style.

## Resumen

- S3 es almacenamiento de **objetos**, no de archivos.
- **Bucket + key** identifican cada objeto.
- Conocer las **storage classes** entra mucho en el examen.
- **Versioning** te salva de borrados accidentales.
- **Pre-signed URLs** son la forma estándar de subir/bajar sin exponer credenciales.
- **Object Lock** sirve para compliance.
- En código, recordá `forcePathStyle: true` con Floci.
